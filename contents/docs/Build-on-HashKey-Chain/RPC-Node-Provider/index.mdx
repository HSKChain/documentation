## Running Your Own Node

Self-hosting a HSKChain node gives you improved reliability, privacy, and control over your blockchain interactions. The supported stack is **op-reth** (execution) + **op-node** (consensus), launched with Docker Compose from the [`fullnode-sync`](https://github.com/HSKChain/fullnode-sync) repository.

<Note title="op-geth end of support" type="warning">
  op-geth has reached end-of-support and is no longer used by `fullnode-sync`. Migrate to op-reth. Existing op-geth datadirs are **not** compatible with op-reth — start a fresh `reth` volume or restore an official op-reth snapshot.
</Note>

### Prerequisites

- Git
- Docker and Docker Compose
- OpenSSL
- `curl` (used by `./fetch-config.sh` to download genesis / rollup configs)
- Access to an Ethereum L1 RPC endpoint
- Access to an Ethereum L1 Beacon endpoint
- Minimum system requirements:
  - 16GB RAM
  - 4 CPU cores
  - 1TB SSD storage (for archive node)
  - 500GB SSD storage (for full / pruned node)

### Setup Instructions

1. **Clone the repository**

```bash
git clone https://github.com/HSKChain/fullnode-sync
cd fullnode-sync
```

2. **Generate JWT secret**

This JWT secret is used for secure communication between the execution and consensus layers.

```bash
openssl rand -hex 32 > ./jwt/jwt.txt
```

3. **Configure environment variables**

Copy the example for your network, then fill in `L1_RPC` and `L1_BEACON`:

```bash
# Testnet
cp .env.example.testnet .env

# Mainnet
cp .env.example.mainnet .env
```

Or paste one of the configuration templates below into `.env`.

4. **Fetch genesis / rollup configs**

op-reth and op-node images are minimal and do not ship download tools, so configs are fetched on the host into `./config`:

```bash
chmod +x ./fetch-config.sh
./fetch-config.sh
```

5. **Start the node**

```bash
docker compose --env-file .env up -d
```

6. **Monitor the node**

```bash
docker compose logs -f reth
docker compose logs -f node
```

<Note title="Faster sync">
  Syncing the execution layer from genesis can take a long time. To bootstrap op-reth from an official chaindata snapshot instead, see the **Syncing from a Snapshot** section below.
</Note>

### Key environment variables

| Variable | Description |
| --- | --- |
| `RETH_IMAGE` | op-reth Docker image |
| `NODE_IMAGE` | op-node Docker image |
| `RETH_MODE` | `full` (pruned, passes `--full`) or `archive` (full history) |
| `RETH_TRUSTED_PEERS` | Comma-separated enode URLs for op-reth |
| `GENESIS_URL` / `ROLLUP_CONFIG_URL` | Sources used by `./fetch-config.sh` |
| `SEQUENCER_HTTP` | Sequencer endpoint for tx forwarding |
| `L1_RPC` / `L1_BEACON` | Ethereum L1 execution + beacon endpoints |
| `P2P_STATIC` | op-node libp2p static peers |

Recommended image tags:

```bash
RETH_IMAGE=us-docker.pkg.dev/oplabs-tools-artifacts/images/op-reth:v2.8.1
NODE_IMAGE=us-docker.pkg.dev/oplabs-tools-artifacts/images/op-node:v1.19.11
```

## Sanity checks

```bash
# chain id — mainnet 177 (0xb1), testnet 133 (0x85)
curl -s http://127.0.0.1:8545 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"eth_chainId","params":[],"id":1}'

# sync status
curl -s http://127.0.0.1:8545 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"eth_syncing","params":[],"id":1}'

# block number
curl -s http://127.0.0.1:8545 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}'

# op-node sync status
curl -s http://127.0.0.1:9545 -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"optimism_syncStatus","params":[],"id":1}'
```

During the initial EL-driven sync (`--syncmode=execution-layer`), `eth_blockNumber` may stay at `0x0` while op-reth downloads headers/bodies, and `safe` / `finalized` may remain `0` until derivation catches up. This is expected.

## Syncing from a Snapshot

Syncing a HSKChain node from genesis can take a long time — especially for an archive node. To get up and running faster, bootstrap **op-reth** from an official chaindata snapshot instead of syncing the execution layer block by block.

<Note title="Before you start">
  These are **archive** op-reth chaindata snapshots compressed with Zstandard (`.tar.zst`). Make sure you have `curl`, `tar`, and `zstd` installed, and enough free disk space (see the archive-node storage requirement in the Prerequisites section). Set `RETH_MODE=archive` when restoring an archive snapshot.
</Note>

### Restore Steps

1. **Stop the node if it is already running**

```bash
docker compose --env-file .env down
```

2. **Download the op-reth snapshot for your network**

```bash
# Mainnet
curl -fL -o mainnet-reth-archive-chaindata.tar.zst \
  "$(curl -fsSL https://snapshot.hashkeychain.net/mainnet/reth/latest.txt)"

# Testnet
curl -fL -o testnet-reth-archive-chaindata.tar.zst \
  "$(curl -fsSL https://snapshot.hashkeychain.net/testnet/reth/latest.txt)"
```

3. **Inspect the archive layout**

Check the top-level folder inside the archive so you extract it to the right place. With the default Compose setup, the op-reth datadir is the Docker volume mounted at `/data` for the `reth` service.

```bash
tar --use-compress-program=zstd -tvf mainnet-reth-archive-chaindata.tar.zst | head
```

Find the host path for the volume (name may vary by project directory):

```bash
docker volume ls | grep reth
docker volume inspect <project>_reth
```

4. **Extract the snapshot into the op-reth data directory**

```bash
# extract directly (requires a tar build with zstd support)
tar --use-compress-program=zstd -xvf mainnet-reth-archive-chaindata.tar.zst -C <RETH_DATA_DIR>
```

If your `tar` does not support zstd, decompress first and then extract:

```bash
zstd -d mainnet-reth-archive-chaindata.tar.zst -o chaindata.tar
tar -xvf chaindata.tar -C <RETH_DATA_DIR>
```

<Note title="Placement" type="warning">
  Extract so the op-reth database files land in the directory mounted as `/data` for the `reth` service. Inspect the archive layout first — if the tarball has a wrapping top-level folder, adjust `-C` / `--strip-components` accordingly.
</Note>

5. **Set archive mode, then start the node**

```bash
# in .env
RETH_MODE=archive

docker compose --env-file .env up -d
```

6. **Verify the node resumes from the snapshot**

```bash
docker compose logs -f reth
```

op-reth should recognize the existing datadir, resume near the snapshot height, and then catch up to the chain head via the P2P network / EL sync.

## Hardfork / config upgrade

When `genesis.json` / `rollup.json` change (or client images need bumping):

1. Update `RETH_IMAGE`, `NODE_IMAGE`, and config URLs in `.env` if needed.
2. Pull images if tags changed: `docker compose --env-file .env pull`
3. Run the upgrade helper (re-fetches `./config` and restarts; does **not** wipe chain data):

```bash
chmod +x ./upgrade.sh
./upgrade.sh
```

Unlike op-geth, op-reth does not need a separate `init` step — it loads `--chain` from genesis on startup.
